### Claude:

Here is the batch plan built from your answers. Three agents run now from `main`, each in its own worktree and branch. The menu batch waits for a later session, after core is on `main`.

**Answer to your question:** yes, the registry data is available in the world creation menu. The create screen loads the datapack registries and binds their tags and data maps into the `WorldCreationContext`, so the menu and the preview can read variations, placements and lists before a world exists.

## Batch 1: Core data and level binding (`claude/shaft-registries`)

- **Three dynamic registries**, none synced to the client. `aerolite:shaft_variation` with entries stone, mossy, tuff, deepslate, copper, mud, andesite, diorite, granite, nether, blackstone, soul, quartz, end, purpur. The entry JSON holds bias, decay scale, decay threshold, erosion threshold, interior, wall and path. The weight leaves the entry. `aerolite:shaft_placement` with entries `aerolite:default`, `minecraft:overworld`, `minecraft:the_nether`, `minecraft:the_end`. A dimension looks up the placement under its own id and falls back to `aerolite:default`. `aerolite:variation_list` with entries overworld, nether and end. Each holds a map of variation id to weight and nothing else.
- **Two data maps.** `aerolite:shaft_variations` on the dimension registry maps a dimension id to variation ids with weights. It ships empty, so no world gets shafts until a world datapack adds a value. `aerolite:cloud_height` on the dimension type registry ships `aerolite:overworld` at -32. The cloud packet reads it.
- **Datagen** writes all entries and both data maps. The Java constants in `ShaftVariation` go away.
- **Level binding.** The shafts step reads a per-level holder, not the generator. The agent builds both a NeoForge level attachment and a mixin duck interface, times a chunk paint loop with each, and keeps the faster one. If the difference is inside the noise, the attachment stays per the project mixin rule. The report states the numbers.
- **Shim generator.** `AeroliteChunkGenerator` stays registered and keeps carrying settings so 0.2.x worlds load and the current menu keeps working until the menu batch lands. On first load of a level whose dimension has no data map value, the binding takes the shim settings and writes `<world>/datapacks/aerolite_shafts/` with the data map values and placement entries. Vanilla enables a newly found world datapack by itself.
- **Tests and CLAUDE.md.** JUnit and GameTests move to the new types. CLAUDE.md gets a new Data section and edits in the Shafts and Dimension sections only.

## Batch 2: Local runtime mods (`claude/runtime-mods`)

- Aether, Applied Energistics 2, Bumblezone, Gaia Dimension and Voidscape join `localRuntime`, each with `transitive = false` and every companion mod it needs listed on its own line. Versions go in `gradle.properties`. Each repository gets its `includeGroup` lines and a comment with the mods it serves.
- No `mods.toml` change. Done means both dependency checks pass with `--refresh-dependencies` and a muted client reaches the title screen with every mod listed in the log.
- CLAUDE.md edits in the Dependencies section only.
