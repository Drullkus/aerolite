### Claude:

The tool is not confused by a resume. Its resume check is too loose, and your two "0.3.0 batch fixes" conversations trip it.

**The check.** The function `find_superseded` in [claude_transcript_to_md.py:280](llm/tools/claude_transcript_to_md.py:280) looks for an earlier transcript on the same calendar date whose text holds the first 300 characters of the opening prompt. It does not compare the start time.

**What happened today.** Three sessions on 2026-10-31 open with the identical prompt text "Please batch these fixes for Opus subagents for me to release a 0.3.0...":

| Session | Start (UTC) | What it is |
|---|---|---|
| `80f433d5` | 06:49:04 | The first 0.3.0 batch conversation. Its transcript is committed. |
| `1143d92a` | 20:42:21.009 | A new conversation with the same opening prompt. |
| `565ea277` | 20:42:21.009 | The desktop app resume of `1143d92a`. Same start to the millisecond. |

An export of either 20:42 session finds the 06:49 transcript by the prompt text and reports it as superseded. I confirmed this by calling the function directly. The committed 06:49 transcript is intact and the working tree is clean, so nothing was lost.

**The fix.** A true resume copies the history, so the first user record keeps its exact timestamp. The check can require the same start time to the second: glob `transcript_<date>_<HH-MM>_*.md` and require the header line `| Started | ... |` to match, in addition to the prompt text. With that rule, `565ea277` still links to `1143d92a`, and the 06:49 transcript is left alone.
