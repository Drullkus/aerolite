## Prompt 1 — 2026-11-14 01:32:43 UTC

### User:

Create a technical plan for Opus subagents to use, it shall go on my approval.

It's time to create the island types. The goal is to provide me with tools creating my own island types that will become prefabs. Sky island instances come in varieties, like Pillars do.

Each island variation dispatches its own Density Function and Biome Source. Empty becomes an island variation. Island variations are chosen via weighted list in generation. An island variation can be a weighted sub-list of island variations.

All current sliders get taken by island variations, besides jitter and separation of pre-jitter cell sites. The plan stays that only one layer of voronoi cells generate islands, with sites above and below generating empty, only to influence generation of cells in that middle layer.

Per-variation island cell sizes become weights, defaulting to 0.5 and operates by fractional values [0.0..1.0]. They become distance multipliers for choosing which blockpos goes to each cell, where the higher weight causes a cell to take more space from cells with lesser weight. This uses min-max sliders and the weight is chosen per variation instance.

## Where the time goes

Each batch runs the full check list at least twice: once by the build subagent and once by the check subagent. ## 1. A process rule, with no code

- The build subagent runs only the test classes of the packages that it touches, with `./gradlew test --tests 'us.drullk.aerolite.world.island*'`.
- The full check list runs once per batch, at the end, by the check subagent.
- A path rule gates the three slow runs:

| Run | Runs when the diff touches |
|---|---|
| GameTest server | `world/`, data generation or a GameTest class |
| `runData` | data generation or a registry codec |
| Islands probe | `client/`, `devtools/` or `CellGeometry` |

This halves the full runs and keeps one full run per batch, so no change stays untested.

## 2. A selector by dependency

Gradle has no test selection by coverage in its free version. The commercial Develocity has one. A small script can do it for this project:

- It takes the changed files from `git diff --name-only main`.
- It reads the class dependencies of `build/classes` with `jdeps`.
- It finds each test class that reaches a changed class, and it prints the `--tests` arguments.

The limits of this selector:

- A static dependency is wider than real coverage. So it selects too many tests, never too few, for plain Java calls.
- It does not see a link through reflection: Beanification injection, a `@Directory` list, a codec that a registry finds.
- It does not see a data file, for example `prototypes/cells/tables.json`. A changed resource or a changed `build.gradle` must give a full run.
- It cannot select GameTests. They run in one server start, and the start is the main cost.

Real coverage per test with JaCoCo is a fourth way. I did not test whether its agent works with the NeoForge class transformers, so I do not offer it as working.

## 3. Speed without selection

- Drop `--rerun`. Gradle then skips the test task when no input changed, for example when the check subagent makes no fix.
- Turn on parallel execution of JUnit for the pure logic classes.
- Tag the slow sweep tests, and leave them out of the runs during a batch.

## The trade

Way 1 costs nothing and applies from batch 2 on. Way 2 costs one small tool and its upkeep, and it saves time only on JUnit. Way 3 changes `build.gradle` and needs its own check that the game classpath tolerates parallel tests.

The check subagent of batch 1 still runs under the current rule. I do not interrupt it.

### Claude:

The new caches are the same kind as yours. The difference is the size of one entry, and that is the whole problem.

## Your caches and the new caches

| | Your `CelledSpaceGenerator` | The new `VoronoiLattice` |
|---|---|---|
| Site per lattice index | `cells`, line 138 | `sites` |
| Cell per lattice index | `voronoiCells`, line 143 | `walls` |
| Limit on the entry count | None. The maps grow with the explored world. | Fixed: 4096 sites, 256 cells. A new entry replaces an old one. |
| Content of one cell entry | Only the neighbors that `tryAddVector` keeps, from a fixed scan radius. | Every candidate site inside the proven wall reach. |
| Size of one cell entry | Small, a few dozen vectors. | 416 planes at the shipped sizes, about 17 KB. |

Both are pure functions of the index, so a wiped entry costs only time, as your comment says. The new lattice has a third cache, `searches`: the candidate sites of the owner lookup around one box.

## Where the problem is

- At the shipped sizes of 256 by 128, a full lattice holds about 5 MB. That is no problem.
- The entry size follows the proven reach. The reach counts boxes along the short axis.
- The old type `aerolite:voronoi_islands` measures plain distance. A flat cell of 1024 by 32 then reaches across many rows, and a full lattice holds about 61 MB.
- At its JSON bounds of 16 by 4096, one cell entry is about 110 MB. On `main` that lattice has no cache and is only slow.
- The new island function scales the Y axis, so its entry has a fixed top of 666 planes, about 7 MB per full lattice.

So only the old type with extreme sizes can use much memory. A slider end reaches 61 MB. Only a hand-written data pack reaches the gigabytes.

## Two ways to limit it

- **Size guard:** a lattice whose one entry is above a fixed size uses no cache. It is then as slow as on `main`. The values do not change. This is a few lines.
- **True walls only:** like your `tryAddVector`, a cell entry keeps only the walls that bound the cell. An entry shrinks to a few dozen planes at every size, and the gauge gets faster. The clip of each new cell costs time once. The `searches` cache still needs the size guard.

The plane test alone does not suffice. It can drop a real wall, so it misses positions at cell corners.

## What `tryAddVector` tests

For the cell center O, a neighbor `v` in the list and a new neighbor `d`:

- `v · d > d · d` removes `v`. The site `v` lies beyond the plane through the site `d`.
- `v · d > v · v` rejects `d`. The site `d` lies beyond the plane through the site `v`.

Both lines say the same thing in another form: a neighbor B goes away when another site A lies inside the sphere whose diameter is the line from O to B. This is the Gabriel neighbor test.

## What it keeps and what it drops

- It keeps each wall whose face holds the midpoint between O and that neighbor. These are the large faces.
- It drops a wall whose face does not hold that midpoint. Such a wall can still be a real face of the cell. It is a small face at a corner, from a neighbor that sits behind another neighbor at a slant.
- The plane through A is at the site A, not at the wall between O and A. So "B is beyond that plane" does not prove that the wall of B lies outside the cell.

## One example in 2D

- O = (0, 0), A = (1, 0), B = (1.05, 0.2), and a third neighbor C = (0, 1).
- The test drops B, because B · A = 1.05 is above A · A = 1.
- The point (0.5, 0.45) passes the walls of A and C. So the filtered cell holds it.
- Its squared distance to O is 0.4525. Its squared distance to B is 0.365. So the point belongs to B.

The filtered cell is the true cell plus such corner pieces. Jitter makes this case: two neighbors in nearly one direction, with the far one a little to the side.

## What this means for the lattice

- The gauge is the largest plane value. With a dropped real wall, the gauge is too small in that corner, and the island body is wrong there.
- The values then differ from `main`, so the test at tolerance 0 fails.
- No test on two planes can prove that a wall is spare. Two planes that are not parallel never hold one another. Only the corner points of the cell prove it.

So the subagent keeps the test on the vertices of the cell: it drops a plane only when the plane lies beyond every vertex by a margin. That costs one clip per cached cell, once. I did not change its instructions.
